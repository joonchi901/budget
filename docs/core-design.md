| 항목 | 기준 |
| --- | --- |
| 문서 버전 | v3.1 |
| 갱신일 | 2026-09-17 |
| 적용 모델 | 수입/지출 원장, 사용자 정의 태그, 명시적 자산 배분, 별도 자산 이동·잔액 조정 |
| 기능·시스템 기준 | [기능 정의서](./functional-requirements.md), [시스템 구성 기준서](./system-architecture-baseline.md) |
| 구현·검증 상태 | [구현 현황](./implementation-status.md)에서 소스 구현과 실행 증거를 구분 |

이 문서는 현재 코드의 데이터 관계와 돈이 반영되는 기준을 설명한다. 전체 기능의 완료를 의미하지 않는다. 이전의 고정 태그 규칙과 수입/지출/저축/이체 네 가지 거래 모델은 현재 모델로 대체한다.

## 1. 업무 경계

| 정보 | 기록·집계 위치 | 다른 금액에 미치는 영향 |
| --- | --- | --- |
| 수입·지출 | 하나의 원본 가계부 | 자산 배분을 명시했을 때만 해당 자산 증감 |
| 예산 | 각 가계부의 계획 | 자산·저축 변동 없음 |
| 태그 유형·옵션 | 거래·자산의 사용자 정의 분류 | 이름·선택·색상·순서만으로 금액 변동 없음 |
| 자산 이동 | 별도 자산 변동 이력 | 두 자산의 감소·증가. 가계부 거래 생성 없음 |
| 잔액 조정 | 별도 자산 변동 이력 | 기록일 기준 잔액과 목표 잔액의 차액. 수입·지출·저축 실적 변화 없음 |
| 저축 | 저장 당시 자산 변동의 통계 | 수입·지출의 거래 종류와 구분 |
| 카드 청구 예상 | 카드 정보 | 구매 지출을 다시 만들거나 계좌 잔액을 자동 차감하지 않음 |

메인 연결은 원본 거래를 조회 범위에 포함하는 동작이다. 하위 거래를 복사하거나 자산 효과를 다시 생성하지 않는다. 목적 가계부의 수정은 원본 화면에서 하고, 예비금은 다른 자산과 동일하게 관리한다. 여행 예산과 예비금은 자동 연결하지 않는다.

## 2. 데이터 관계와 소스

[공유 타입](../src/shared/types.ts)이 클라이언트·서버 계약이다. [초기 스키마](../migrations/0001_schema.sql) 위에 [태그·자산 마이그레이션](../migrations/0002_tags_assets.sql)을 적용한다.

| 데이터 | 역할 |
| --- | --- |
| `Ledger` | 단일 부모 트리, 독립 기간·총예산·부모 연결·형제 순서·수정 버전 |
| `User.role` | admin/user. 현재 DB 역할로 구조·역할 변경 권한 검사 |
| `Household.hierarchyVersion` | 가구 구조·역할 변경의 공통 충돌 버전. 개별 레코드 버전·전체 revision과 별도 |
| `Transaction` | 수입 또는 지출, 원본 가계부·날짜·금액·귀속·결제수단·태그 ID·자산 배분 |
| `Allocation` | 자산 ID와 양의 금액. 비어 있거나 거래 금액 전체를 자산별로 나눈 목록 |
| `TagGroup` | 단일/복수 선택, 거래/자산 사용 위치, 전체/지정 가계부 범위, 순서·보관·버전 |
| `Tag` | 유형에 속한 옵션 ID·이름·색상·순서·보관·버전 |
| `Asset` | 자산/부채, 최초 잔액·현재 잔액, 자산 태그, 명시적 저축 집계 여부와 버전 |
| `AssetOperation` | 자산 이동 또는 잔액 조정의 날짜·사유·대상·금액·목표 잔액·작성자·취소 이력 |
| `AssetMovement` | 거래 또는 자산 변동에서 발생한 실제 증감, 당시 저축 집계액·날짜·사유·작성자 |
| `PaymentMethod` | 카드·통장·현금의 관리 정보. 자산 잔액의 또 다른 원본이 아님 |

DB의 현재 자산 효과는 `asset_effects`에 저장한다. 각 효과는 거래 또는 자산 변동 중 정확히 하나를 원본으로 가진다. 이전 `asset_movements`와 고정 `rules`는 이관·감사 목적으로 남지만 현재 화면의 금액 처리에는 사용하지 않는다.

## 3. 잔액과 명시적 배분

```text
현재 잔액 = 최초 기준 잔액 + 유효한 asset_effects.amount의 합계
```

### 3.1 수입·지출의 자산 반영

- `allocations=[]`이면 자산에 반영하지 않는다. 태그나 결제수단 이름으로 대상을 추정하지 않는다.
- 배분을 지정하면 같은 가구의 일반 자산, 중복 없는 대상, 양의 정수 금액을 검사한다. 배분 합계는 거래 금액과 정확히 같아야 한다.
- 수입은 각 배분 금액을 더하고 지출은 뺀다. 여러 자산으로 나눠도 가계부 거래는 한 건이다.
- 수정·삭제는 이전 자산 효과를 교체·제거한다. 새 효과를 이전 것 위에 다시 누적하지 않는다.
- 카드 구매에도 명시적 배분은 가능하지만 카드 청구 정보 자체가 추가 자산 효과를 만들지 않는다. 실제 결제계좌 자동 정산은 별도 미구현 정책이다.

### 3.2 이동과 잔액 맞추기

[AssetsView](../src/client/AssetsView.tsx)에서 자산을 추가·수정하고, 두 일반 자산 사이 이동과 자산/부채의 기록일 기준 잔액 맞추기를 기록한다.

이동은 보내는 자산의 감소와 받는 자산의 증가를 함께 저장한다. 잔액 맞추기는 당시 잔액과 목표 잔액을 비교하여 차액을 저장한다. 두 경우 모두 날짜·사유·작성자를 남긴다. 자산 버전을 검사하므로 다른 변경을 모르고 잔액을 덮어쓰지 않는다.

변동을 취소하면 잔액 효과는 제거하고 원본은 취소 이력으로 남긴다. 거래에서 생긴 변동은 자산 화면에서 독립 수정하지 않고 원본 가계부에서 고친다. 최초 잔액은 생성 시 기준이며 이후 평가 조정을 수입으로 입력하지 않는다.

## 4. 저축은 자산 변동 통계

자산의 `trackSavings`는 사용자가 명시하는 설정이다. 이름이나 자산 태그와 무관하다. 저장 시 효과에 `savings_tracking`과 `savings_amount`를 기록하며 [savingsSummary](../src/shared/selectors.ts)는 그 월의 저장값을 합산한다.

| 변동 | 저축 반영 |
| --- | --- |
| 일반 자산 → 저축 집계 자산 | 유입 +금액 |
| 저축 집계 자산 → 일반 자산 | 인출 +금액 |
| 저축 집계 자산끼리 이동 | 양쪽 모두 0 |
| 일반 자산끼리 이동 | 0 |
| 저축 집계 자산에 배분한 수입 / 지출 | 유입 / 인출 |
| 최초 잔액 / 잔액 조정 | 0 |

순저축은 유입−인출이다. 가구 전체 자산 통계이므로 선택한 가계부의 수입·지출 합계와 조회 범위를 구분한다.

설정을 바꿔도 과거 실적은 소급 변경하지 않는다. 기존 거래에서 같은 자산의 배분을 수정하면 당시 집계 여부를 유지한다. 새 대상 자산에 처음 배분하는 효과에는 현재 설정을 사용한다. 변동 취소는 저장된 해당 효과를 제거한다. 수동 전체 재분류는 현재 기능이 아니다.

## 5. 사용자 정의 태그

[TagFields](../src/client/TagFields.tsx)는 유형별 검색·선택·새 옵션 생성을 제공하고, [TagManager](../src/client/TagManager.tsx)는 유형·옵션의 이름·선택 방식·사용 범위·순서·색상·보관/복원을 관리한다.

- 거래용 유형은 모든 가계부 또는 지정 가계부에서 사용한다. 자산용 유형은 공유 자산에 사용한다.
- 단일 선택은 유형당 최대 하나, 복수 선택은 여러 옵션을 허용한다.
- 거래·자산 모두 옵션 ID를 저장한다. 이름이나 색상을 바꿔도 금액과 과거 선택은 보존한다.
- 보관·범위 축소 후에는 새 선택을 제한하고 기존 선택은 조회한다. 영구 삭제로 과거 내역을 깨뜨리지 않는다.
- 사용 중인 복수 선택 유형을 단일로 바꾸는 등 기존 기록과 충돌하는 변경은 서버 검증 대상이다.
- 분석 조건은 같은 유형 안에서 OR, 유형 사이에서 AND다. 옵션별 합계는 복수 선택 때문에 고유 거래 총액보다 클 수 있다. 미분류·보관 옵션도 과거 분석에서 유지한다.

태그의 특정 이름이나 옵션을 선택해 금액을 바꾸는 고정 규칙은 없다. 조건 기반 자동 배분은 후속 설정 기능이며 현재 명시적 배분과 별도로 설계한다.

## 6. 대표 흐름

| 흐름 | 결과 |
| --- | --- |
| 여행 예산 30만 원 설정 후 지출 8만 원 입력 | 여행 잔여 예산 22만 원. 배분을 입력하지 않았으면 자산 변화 없음 |
| 메인에 여행 가계부 연결·해제·재연결 | 조회 범위만 변경. 원본 거래·자산·카드 사용 사실은 보존 |
| 생활 지출 2만 원을 예비금에 명시 배분 | 지출 2만 원과 예비금 −2만 원. 태그만 선택한 경우에는 차감 없음 |
| 일반 자산에서 저축 집계 자산으로 10만 원 이동 | 가계부 수입·지출은 그대로, 저축 유입 10만 원 |
| 잔액 49만 원을 확인 금액 50만 원으로 맞춤 | +1만 원 조정 이력. 수입·지출·저축 합계 변화 없음 |
| 거래 입력 중 없는 옵션 생성 | 사용자 옵션을 만들고 선택. 자산 배분 값은 자동 변경하지 않음 |

계획 화면에서 월·주·기간·항목 예산, 수입/지출/저축 목표, 급여 배분, 행사, 결제 일정을 관리한다. 정확히 대응하는 월 총예산을 우선하며 목적 전체 예산과 비교할 때는 실제액도 같은 전체 기간을 사용한다. 계획 저장만으로 거래나 자산 변동을 만들지 않는다. 카드 예상액은 마감일·납부일 기준의 구매 합계이며 할부·취소·이월·은행 휴일 보정은 미지원이다.

## 7. 저장·협업

[저장 계층](../src/server/storage.ts)은 D1을 업무 데이터의 기준으로 사용한다. 거래·자산 효과·저축 집계값·수정 버전·가구 변경 순번·요청 결과를 원자적으로 반영한다. 재전송에는 같은 요청 ID를 사용하고, 다른 내용으로 ID를 재사용하거나 오래된 버전으로 수정하면 거절한다.

새 거래는 기기 초안과 명시 저장이 기본이며, 사용자가 자동 저장을 켜면 유효 입력을 필드 이탈 후 저장하고 폼을 닫는다. 기존 거래는 유효한 필드 변경을 이탈 후 자동 저장한다. 응답 유실 시 동일 요청 재확인, 충돌 시 입력과 최신 값 구분, 태그 옵션 생성 중 상위 폼의 중복 제출 방지를 구현한다. [useUnsavedGuard](../src/client/components.tsx)는 미저장 입력·확인 중인 요청이 있으면 탭 닫기·새로고침 전에 경고한다. 기기 초안과 불확실한 저장 요청을 가구·사용자·가계부별로 복원하며, 같은 요청 번호를 재사용해 중복 생성을 막는다.

가구당 [HouseholdRoom](../src/realtime/HouseholdRoom.ts) 하나를 사용한다. 접속·선택 위치는 `ledgerId`로 구분하고 저장 후 가구 변경 순번을 전달한다. 누락·재접속·화면 복귀는 `/api/revision`과 전체 `/api/bootstrap` 조회로 복구한다. 변경분 전용 API는 없다.

## 8. v1 데이터 전환과 로컬 범위

[0002_tags_assets.sql](../migrations/0002_tags_assets.sql)은 이전 분류 문자열을 태그 옵션으로 옮기고, 저축·이체 거래를 `asset_operations`로 전환한다. 이전 거래는 감사용으로 보존하고 현재 가계부 조회에서는 수입·지출만 반환한다. 기존 자산별 잔액과 이미 기록한 저축 의미를 보존한다. 특히 이전 저축의 양의 입금 효과만 기존 저축 집계값으로 옮기며 현재 자산 설정으로 다시 해석하지 않는다.

이 전환은 앱 내부 DB 마이그레이션이다. 원본 Excel을 읽거나 변경·이관하지 않는다. 마이그레이션과 [가상 시드](../seeds/demo.sql)는 분리한다. 로컬 시작은 `npm run dev`이며 `.dev.vars` 준비·DB 초기화·빌드 후 Vite 5173과 Worker 8787을 실행한다.

데모 인증은 `DEMO_MODE=true`와 루프백 호스트 조건을 모두 요구한다. Google OIDC의 state/nonce/PKCE·서명 검증과 두 이메일 허용목록을 구현했다. 운영 설정이 없거나 인증되지 않은 데이터 API는 차단한다. 실제 계정·원격 배포·사용량 실측·금융 API 연동은 완료되지 않았다. 이전 v1 검증 결과를 현재 v2 코드의 검증 결과로 사용하지 않는다.

## 10. 관측 잔액·이관·원본 보존

- 자산 기준 잔액의 `openingKind`는 `initial`(실제 발생 시작) 또는 `observation`(처음 확인한 관측)이다. 관측 기준일 이전 잔액은 0으로 추정하지 않고 미확인으로 반환한다. 이후 잔액은 기준액과 날짜별 효과를 합산한다.
- XLSX 이관은 현재 백업에 새 자료를 추가한 후보를 서버에서 검증한다. 후보의 기준 revision이 바뀌면 다시 대조하고 전체 후보를 원자적으로 반영한다. 같은 원본 위치의 재반영과 변경 원문을 구분한다.
- 수입·지출·관리·계획으로 확정 가능한 항목을 가져오며 미확정 날짜·저축/예비금 연결·메모는 `source_records`에 원문·좌표와 함께 보존한다. 검토 상태 변경은 금액 효과를 만들지 않는다.
- 백업은 참조·자산 효과·저축 집계값을 그대로 보존한다. 복원은 효과를 새로 적용하지 않는다. 인증 세션·비밀값은 제외한다.
- 실제 원본 대조와 한계는 [Excel 검증 보고서](./excel-parity-audit.md)를 따른다.

## 8. 가계부 계위와 관리자 권한

[계위·권한 상세 계약](./ledger-hierarchy.md)에 따라 여러 최상위와 임의 깊이의 트리를 지원한다. 모든 단계의 하위 원본을 중복 없이 조회하며 직접 기록만 선택할 수도 있다. 계위 변경은 가구 전체 구조 버전과 현재 관리자 권한을 D1 저장 배치에서 함께 검사한다. 부모 이동 시 그 노드의 분류 대응을 비우고, 사용자 확인 후 새 부모 기준으로 다시 설정한다. `0012_hierarchy_roles.sql`로 역할·계위 버전·형제 순서를 추가하며 거래·자산 효과는 변경하지 않는다.
