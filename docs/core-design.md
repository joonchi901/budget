# 핵심 가계부 흐름 설계

| 항목 | 기준 |
| --- | --- |
| 작성일 | 2026-09-16 |
| 적용 범위 | 로컬에서 검증할 거래·가계부 연결·자산 규칙·카드 정보·공동 사용의 첫 구현 |
| 기능 기준 | [기능 정의서](./functional-requirements.md) |
| 시스템 기준 | [시스템 구성 기준서](./system-architecture-baseline.md) |
| 구현 상태 | [구현 현황](./implementation-status.md)에서 별도로 관리 |

이 문서는 전체 기능 중 먼저 구현할 핵심 흐름의 업무·데이터 경계를 정한다. 기능 정의서의 전체 범위를 줄이지 않는다. 코드가 없는 항목은 설계 기본안이며, 소스·테스트와 대조한 구현 여부는 구현 현황에 기록한다.

## 1. 이번 구현의 경계

로컬 Cloudflare Worker·D1·Durable Object와 웹 화면을 연결한다. 가상 사용자 두 명으로 원본 거래 저장, 서로 다른 가계부의 통합 조회, 거래에 연결된 자산 변동, 저장 후 상대 화면 갱신을 확인한다.

- 실제 OIDC 계정 등록, 원격 배포와 무료 사용량 측정은 후속 작업이다.
- 데모 세션은 로컬에서만 허용한다. 운영 환경에서 실제 인증이 준비되지 않았을 때 데모 인증으로 대체하지 않는다.
- 원본 XLSX를 읽거나 가져오지 않는다. 입력 예시와 초기 데이터에는 가상 자료만 사용한다.
- 통장은 결제수단의 관리 정보다. 통장 정보를 자산 합계에 다시 더하거나 거래 입력만으로 계좌 잔액을 자동 계산하지 않는다.
- 월급 배분·주별 예산·경조사·전체 분석 등 남은 필수 기능은 구현 현황에 후속 범위로 유지한다.

[auth.ts](../src/server/auth.ts)의 데모 허용 조건은 `DEMO_MODE === 'true'`와 요청 주소의 루프백 호스트 조건을 모두 만족하는 것이다. 현재 실제 OIDC는 없으므로 조건을 충족하지 않는 데이터 API는 `AUTH_NOT_CONFIGURED`로 차단한다. 이 동작을 운영 로그인 구현으로 취급하지 않는다.

가상 데이터는 구조 변경용 마이그레이션과 분리한 [seeds/demo.sql](../seeds/demo.sql)에서 로컬 초기화 명령으로 넣는다. 운영 마이그레이션 실행만으로 가상 사용자·거래를 만들지 않는다. `npm run dev`는 로컬 DB 준비와 웹 빌드 후 웹·Worker 서버를 함께 시작한다. 예시는 `INSERT OR IGNORE`로 넣어 기존 값을 덮어쓰지 않는다. 명령의 실행 검증 여부는 구현 현황에서 확인한다.

## 2. 계산과 소유의 불변 규칙

| 대상 | 반드시 지킬 규칙 |
| --- | --- |
| 거래 원본 | 거래는 하나의 가계부에 속한다. 메인 연결은 거래 복사가 아니다. |
| 메인 집계 | 직접 입력한 거래와 연결된 하위 거래를 거래 ID 기준으로 한 번만 합산한다. |
| 하위 수정 | 메인에서 하위 거래를 선택하면 원본 가계부로 이동한다. 수정·삭제 요청도 원본 소속을 검사한다. |
| 연결 변경 | 연결·해제·재연결은 조회 범위만 바꾼다. 자산 효과와 카드 이용 사실은 유지한다. |
| 예산 | 계획 금액이다. 가계부 생성·예산 설정·메인 연결은 자산 금액을 바꾸지 않는다. |
| 예비금 | 투자금·전세금 등과 같은 일반 자산 항목이다. 여행 예산의 배정금으로 취급하지 않는다. |
| 분석 태그 | 검색·집계의 표시다. 이름만으로 자산 효과를 추정하지 않는다. |
| 처리 규칙 | 선택한 규칙의 대상·방향·금액을 명시하고 저장 전에 결과를 보여준다. |
| 자산 조정 | 평가 금액이나 기준 잔액의 수동 정정은 별도 자산 변동이다. 생활 수입 거래로 생성하지 않는다. |
| 카드 | 구매만 소비 지출이다. 예상 청구액·납부일 표시로 지출을 다시 만들지 않는다. |
| 귀속·입력자 | 지출 귀속과 결제수단 소유자를 입력·수정자와 구분한다. 입력·수정자는 서버 세션에서 기록한다. |
| 집계 날짜 | 입력 시각 대신 실제 거래일로 월을 결정한다. 활동 기간 밖 선결제도 기록할 수 있다. |

## 3. 데이터 관계

공유 계약은 [src/shared/types.ts](../src/shared/types.ts), 초기 저장 구조는 [0001_schema.sql](../migrations/0001_schema.sql)에 정의한다. 아래는 논리적 관계이며 화면의 행 번호를 식별자로 사용하지 않는다.

| 데이터 | 관계·역할 |
| --- | --- |
| 공동 공간·구성원·세션 | 접근 가능한 공유 범위와 실제 작성자를 결정한다. 로컬 가상 세션과 운영 인증을 구분한다. |
| 가계부 | 메인 또는 목적 가계부. 독립 기간·예산·관리 항목과 메인 연결 여부를 가진다. |
| 거래 | 원본 가계부, 실제 거래일, 성격, 금액, 귀속, 분류, 결제수단, 태그, 수정 버전을 가진다. |
| 자산·부채 | 공동 공간의 공유 항목. 기준 금액과 변동으로 금액을 관리하며 특정 가계부 예산에 종속되지 않는다. |
| 자산 변동 | 직접 조정 또는 거래 규칙의 결과. 거래에서 발생했다면 원본 거래와 적용 규칙을 추적할 수 있어야 한다. |
| 결제수단 | 카드·통장·현금 등의 관리 정보. 여러 가계부의 거래가 같은 결제수단을 참조할 수 있다. |
| 태그·처리 규칙 | 분석 태그와 금액 효과가 있는 처리의 연결 관계를 관리한다. |
| 변경 순번·수정 버전 | 화면 갱신 누락과 오래된 값으로 덮어쓰는 문제를 각각 감지한다. |
| 저장 요청 기록 | 같은 저장의 재전송으로 거래·자산 효과가 중복 생성되는 것을 막는다. |

### 3.1 자산 금액

```text
현재 자산 금액 = 기준 금액 + 직접 조정의 합계 + 유효한 거래 규칙 효과의 합계
```

거래 수정은 이전 효과를 남긴 채 새 금액을 추가하는 동작이 아니다. 이전 반영을 새 반영으로 교체한다. 삭제한 거래의 효과도 현재 금액에 남아서는 안 된다. 저축·이체와 자산 조정은 소비 지출을 늘리지 않는다.

초기 스키마는 `assets.opening_balance`와 거래별 `asset_movements`를 정의한다. 직접 평가·조정의 별도 입력·이력은 후속 범위이며, 이를 위해 수입 거래를 대신 만들지 않는다. `asset_movements`는 적용 규칙 ID·버전과 현재 효과를 기록하고, 거래별 동일 자산의 중복 효과를 제한한다.

부채는 자산과 구분하여 순자산에서 차감한다. 기준일·월별 평가·음수 허용 등 세부 정책과 전체 대출 조건 관리는 기능 정의서의 후속 상세 범위를 따른다.

### 3.2 조회 범위

| 화면 | 금액의 원본 |
| --- | --- |
| 목적 가계부 | 해당 가계부에 속한 거래 |
| 메인 직접 거래 | 메인에 직접 속한 거래 |
| 메인 통합 | 메인 직접 거래와 현재 연결된 하위 가계부의 고유 거래 |
| 자산 | 공동 공간의 자산 기준 금액·변동. 메인 연결 여부와 무관 |
| 카드·통장 | 해당 결제수단을 사용한 공동 공간 전체 거래. 메인 연결 여부와 무관 |
| 태그 분석 | 선택한 조회 범위의 거래. 복수 태그별 금액 합계와 고유 거래 총액을 구분 |

현재 화면에서 메인 예산은 가계부의 단일 기준액과 선택 월 지출을 비교하고, 목적 가계부의 총예산은 그 가계부의 전체 거래 기간 지출과 비교한다. 월마다 다른 예산과 항목별 예산을 편집·보관하는 기능은 후속 구현이다. 분석 화면은 복수 태그 중 하나라도 포함된 거래를 모으고, 같은 거래 ID를 다시 합산하지 않는다.

## 4. 태그 처리와 카드 표시

### 4.1 태그 규칙

1. 거래 성격·금액과 지정 태그를 읽는다.
2. 분석 표시와 명시적 처리 규칙을 구분한다.
3. 자산 증감이나 이체가 있으면 대상과 금액을 검증한다.
4. 적용 결과를 보여주고 거래·자산 효과를 함께 저장한다.
5. 수정·삭제·재전송·조회 갱신에서도 효과가 한 번만 반영되게 한다.

공유 계약의 처리 종류는 자산 연결 지출(`asset-expense`), 자산 연결 수입(`asset-income`), 저축(`saving`), 이체(`transfer`)다. 자산 연결 수입은 실제 수입 거래의 자산 반영이며 평가·정정 입력의 대체 수단이 아니다. 실제 지원하는 입력 조합·분할 범위와 규칙 관리 UI는 구현 현황에 명시한다.

아직 지원하지 않는 조합을 묵시적으로 처리하지 않는다. 규칙 정의 변경만으로 과거 거래를 소급 계산하지 않으며, 과거 재적용과 규칙 편집의 전체 흐름은 별도 구현 여부를 표시한다.

### 4.2 카드 예상 정보

카드 화면의 사용액·예상 청구액·납부 예정일은 거래를 요약하는 정보다. 별도 소비 거래나 자동 계좌 차감을 만들지 않는다. [cardStatement](../src/shared/selectors.ts)는 납부일 직전 마감일을 기준으로 이전 마감일 다음 날부터 해당 마감일까지의 소비 거래를 합산한다. 월말보다 큰 일자는 말일로 보정하고, 마감일과 납부일이 같으면 이전 달 마감을 사용한다.

현재 할부·취소·이월·은행 휴일 보정은 지원하지 않는다. 금융기관의 확정 청구액을 검증했다는 표현을 사용하지 않는다.

## 5. 필수 화면 흐름

| 흐름 | 사용자 동작과 확인할 결과 |
| --- | --- |
| 로컬 공동 사용 시작 | 가상 사용자 중 한 명으로 시작하고 현재 사용자·데모 상태를 확인한다. 다른 브라우저의 사용자와 거래를 공유한다. |
| 독립 목적 가계부 | 목적 가계부를 만들고 기간·총예산을 기록한다. 여행 예산 30만 원을 정해도 자산은 변하지 않는다. 항목별 예산 관리의 전체 흐름은 후속 범위다. |
| 거래 입력·수정 | 원본 가계부에서 입력하고 저장 결과를 확인한다. 거래 수정·삭제 후 목록과 관련 집계를 갱신한다. |
| 메인 연결·이동 | 목적 가계부를 연결해 메인에서 합계를 보고, 거래 수정은 원본으로 이동한다. 연결 해제·재연결로 거래를 복제하지 않는다. |
| 독립 여행 예산 확인 | 여행 거래 8만 원을 기록하면 여행 예산 잔액은 22만 원이다. 자산 규칙을 별도로 지정하지 않았다면 자산은 변하지 않는다. |
| 자산 규칙 확인 | 메인 생활 지출 2만 원에 예비금 차감을 명시하면 예비금 50만 원은 48만 원이 된다. 거래를 1만 원으로 고치면 49만 원이 된다. |
| 카드 정보 확인 | 구매 내역과 예상 청구 정보를 함께 보되 지출 총액은 구매액 한 번이다. |
| 충돌·연결 복구 | 상대 편집 위치와 저장을 확인한다. 충돌 때 내 입력을 보존하고, 재접속 후 최신 저장 내용을 다시 읽는다. |

자산 직접 조정 화면은 후속 구현이다. 도입 시 평가·정정 금액을 자산 변동으로 기록하고 생활 수입·소비 지출 합계는 유지해야 한다.

## 6. 저장·협업 경계

D1을 저장된 업무 데이터의 기준으로 삼고 Durable Object는 접속·편집 위치·변경 알림을 전달한다. 선택 위치는 잠금이 아니다. 화면은 저장 성공을 받기 전 완료로 표시하지 않는다.

첫 UI는 거래·가계부 폼의 명시적 **저장 버튼**으로 저장한다. 기능 정의서의 입력 완료 시 자동 저장은 후속 구현이며 제거한 요구가 아니다. [TransactionForm](../src/client/TransactionForm.tsx)은 저장 응답을 확인하지 못했을 때 같은 요청으로 재확인하고, 충돌 시 현재 입력과 최신 값을 구분한다.

[useUnsavedGuard](../src/client/components.tsx)는 저장 전 입력이나 결과 확인 중인 요청이 있으면 새로고침·탭 닫기 시 브라우저 경고를 요청한다. 경고에서 취소하면 현재 입력과 재확인할 요청을 유지한다. 브라우저 종료를 강행한 뒤 초안을 되살리는 저장소나 완전한 오프라인 편집 기능은 구현하지 않았다.

- API는 사용자·공유 범위·원본 소속·참조·금액·규칙을 검증한다.
- 수정은 읽은 버전을 검사한다. 충돌 시 최신 값과 사용자 입력을 구분한다.
- 거래와 자산 효과는 함께 반영한다. 일부만 성공한 결과를 정상 저장으로 표시하지 않는다.
- 동일 저장 요청을 재전송해도 금액이 다시 반영되지 않게 한다.
- 저장 이후 알림을 보내고, 재접속·화면 복귀·변경 순번 확인으로 누락된 알림을 보완한다.
- 서버가 저장된 변경을 통지한다. 클라이언트가 보낸 임의 메시지를 저장 성공으로 신뢰하지 않는다.
- 협업방의 실제 구성·메시지 계약·검증 결과는 구현 소스에 맞춰 기록한다. 시스템 기준서의 목표 동작을 구현 완료 증거로 대체하지 않는다.

### 6.1 첫 구현에서의 단순화

시스템 기준서 v1.1의 가계부별 방·공유 방 구성을 첫 구현에서는 **가구당 `HouseholdRoom` 하나**로 단순화한다. 접속 정보에 `ledgerId`를 포함해 현재 가계부의 사용자를 구분하고, 저장 후 변경 순번은 같은 가구의 연결에 전달한다. 거래 내용 자체를 클라이언트 메시지로 공동 편집하는 방식이 아니다. 이 구현 선택은 본 문서에 기록하며, 시스템 기준서 v1.1의 해당 구조는 이후 동기화 대상이다.

변경 알림과 `/api/revision`에서 새 순번을 발견하면 bootstrap 조회로 전체 현재 상태를 다시 읽는다. 첫 구현에는 변경분만 반환하는 전용 조회 API가 없다. 두 사용자·가상 데이터로 핵심 복구를 검증하는 범위이며, 데이터가 늘어난 경우의 전송량·조회량은 측정 전이다.

[storage.ts](../src/server/storage.ts)는 D1 `batch` 안에서 요청 기록의 제약 조건으로 기대 버전을 검사하고, 거래·자산 효과·가구 변경 순번·변경 기록·응답 기록을 함께 반영한다. 자산 잔액을 읽고 덮어쓰는 대신 기준 금액과 효과의 합계를 조회한다. 로컬 원자성·동시 요청 검증 결과는 구현 현황에 기록한다.

## 7. 구현 판단 기준

구현 여부는 [구현 현황](./implementation-status.md)의 소스·테스트 근거로 확인한다. 로컬 테스트 통과는 실제 계정 인증, 원격 D1·Durable Object 동작, 장기 미사용 복구, 운영 비용 또는 전체 기능 완료의 증거가 아니다.
